Where SDLS fits

SDLS adds authentication, encryption or both to the contents of Transfer Frames on a space link. It is an extra service of the TM, TC, AOS and USLP protocols, applied inside the data link layer.

One frame, two shapes

Toggle SDLS on and off to see what it adds to a frame.

Functional lens

  • Works on octet-aligned user data inside Transfer Frames.
  • Keeps the frame header formats, so legacy frame processing and SLE services keep working.
  • Scales to any number of virtual channels; header and trailer sizes are fixed per channel for the mission.
  • Not for Proximity-1.

Security lens

  • Algorithm-agnostic: the protocol carries the parameters; CCSDS 352.0 lists recommended algorithms.
  • Protects the frame data and selected header fields, not the RF channel itself.
  • Key management is outside this standard.

Security Associations

A Security Association (SA) is the agreement both ends share about how to protect one direction of traffic: which service, which algorithms and keys, which field lengths, and the running counters.

Explore an SA database

A sample database for a mission with a TC uplink and an AOS downlink. Pick an SA to see its parameters.

Lifecycle

  1. Create the SA with its service type, algorithms and lengths.
  2. Key it: associate the cryptographic key or keys.
  3. Bind it to one or more GVCIDs or GMAP_IDs.
  4. Activate it. Only one SA may be active per GVCID or GMAP at the sender.

Functional lens

  • All frames with the same SPI on a physical channel share one SA; those frames form a Secure Channel.
  • SAs can be preloaded before launch or created in flight, alongside active ones.
  • Service type is exactly one of: authentication, encryption, authenticated encryption.

Security lens

  • Algorithms, modes and lengths are frozen for the SA's life: no in-band downgrade.
  • Sender and receiver databases must stay in sync, or every frame fails.
  • Keys are stored by value or by index into a key store.

    Sending: ApplySecurity

    At the sending end, the link protocol builds a partial frame and calls ApplySecurity. SDLS selects the SA from the GVCID (and GMAP_ID), protects the frame and hands back the part from Security Header to Security Trailer.

    AEAD: what is plaintext, what is AAD

    Primary Header(Segment Hdr / FSH)Security Header
    Frame Data Field
    MAC

    AAD: from the first octet of the Authentication Payload to just before the data field (after masking)

    Plaintext: the Frame Data Field

    Functional lens

    • Input: from the first octet of the Primary Header to the last octet of the data field, with an empty Security Header.
    • MAC may be truncated (least-significant bits dropped) to the SA's MAC length.
    • Pad Length records fill bytes when the mode needs them.

    Security lens

    • Encrypt-then-MAC: the receiver can reject a forged frame before decrypting anything.
    • The sequence number goes into the header before the MAC, so it is authenticated.
    • Only one active SA per channel: no ambiguity about which key protects a frame.

    Receiving: ProcessSecurity

    At the receiving end, ProcessSecurity always verifies and may decrypt. It returns a Verification Status, a status code, and the data between the Security Header and the trailer.

    Pick a scenarioThe diagram highlights the path the frame takes.

    Functional lens

    • Minimum status codes: no failure, invalid SPI, MAC verification failure, anti-replay failure, padding error.
    • Encryption-only SAs skip the MAC and sequence checks.
    • Pad bytes are removed using the Pad Length field.

    Security lens

    • Verify before decrypt; never decrypt a frame that failed.
    • The stored SN moves only after every check passes, so forgeries cannot advance it.
    • Rejected frames may be archived for forensic investigation.

    The authentication mask

    The authentication bit mask decides which header bits go into the MAC. It is ANDed with the frame: ones keep a bit, zeros replace it with zero. Some bits are fixed by the standard, the rest are a mission choice.

    Select a field to see its rule.
    in MAC (mask 1)masked out (mask 0)never in payloadfixed by the standard

    Functional lens

    • The mask must be at least as long as Primary Header through data field; for variable-length TC and USLP frames, size it for the largest frame.
    • Fields completed after ApplySecurity (MC frame count, OCF, FECF) cannot be in the MAC.

    Security lens

    • Default masks leave Spacecraft ID, version and counters unauthenticated. Decide deliberately whether to include them.
    • VCID (and USLP MAP ID, TC Segment Header) are always authenticated, so a frame cannot be moved to another channel unnoticed.

    Replay protection

    A valid MAC proves a frame was made by a key holder, not that it is new. The sequence number and window catch replays: the receiver accepts a frame only if its SN is above the stored value and no more than the window above it.

    Sender next SN1
    Receiver stored SN0
    Accept range1–5

      Try this: set the window to 2 and press "Lose 3 frames" twice. Every later frame is rejected, because rejected frames never update the stored value. Size the window for the worst expected gap in RF reception.

      Functional lens

      • The sender increments by one per frame; the receiver stores the last accepted value.
      • SN lives in its own field (2–8 octets) or in a counter-style IV.
      • Rollover to zero is mission-specific.

      Security lens

      • Replays (SN ≤ stored) and far-future frames (SN > stored + window) are discarded.
      • A window too large weakens the check; one too small locks the link after losses.

      What is covered, what is not

      SDLS protects what passes through ApplySecurity: the Transfer Frame Data Field and authenticated header fields. Anything the link protocol adds afterwards, or that arrives as an already-built frame, is outside its reach.

      Functional lens

      • Unprotected services can still run on the same master channel.
      • TC: one SA per VC. USLP with COPs: the same.

      Security lens

      • COP-1 / COP-P control and CLCW / PLCW in the OCF are spoofable.
      • Frames supplied by external sources (VCF, MCF) carry no SDLS protection.

      Cheat sheet

      Numbers

      • SPI 16 bits; 0 and 65535 reserved
      • Security Header ≤ 64 octets
      • IV 1–32 · SN 2–8 · PL 1–2 · MAC 8–64 octets
      • GCM baseline: header 14, trailer 16
      • TC CMAC baseline: header 6, trailer 16

      Rules

      • SA = simplex, stateful, frozen algorithms
      • One active SA per GVCID / GMAP at the sender
      • TC: one SA per VC; no SAs for idle-data VCs
      • Encrypt-then-MAC; verify before decrypt
      • Accept SN only if stored < SN ≤ stored + window

      Not protected

      • Jamming and traffic analysis
      • OCF, Insert Zone, FECF, MC frame count
      • COP control and CLCW / PLCW
      • VCF / MCF frames from external sources
      • Key management (see 355.1)
