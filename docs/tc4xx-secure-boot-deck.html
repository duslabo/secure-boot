Speaker notes

The ask: switch TC4xx ECUs from the hybrid model (signature at flashing, device CMAC at boot) to verifying the OEM signature at every boot.

Two numbers frame it: ECDSA costs about 5 ms and ML-DSA about 13 ms over a 2 MB image on TC4xx. The CMAC we would save time with has to read the same 2 MB, so the saving is small. The security gain is large: no device secret, no recompute step.

Recommendation

Verify the OEM signature at boot. Drop the on-device CMAC.

One signature

One signature over the image, verified at flashing and again at every boot.

No secret on the ECU

The private key stays in the OEM backend HSM. The ECU holds only the public key anchor.

PQC path built in

ECDSA today, ML-DSA as the target. Anchors for both are provisioned from day one.

Keep the hybrid only where

  • the measured boot-time delta does not fit the startup budget, even with staged verification
  • the ECU is SHE-class with no ECC/SHA acceleration, for example TC3xx

“The CMAC is only as trustworthy as the moment it was computed.”

Speaker notes

Three properties carry the recommendation. One signature, checked twice, means one mechanism to implement, test and argue. Nothing secret lives on the ECU, so there is nothing to extract and no device key to provision per unit. And the verifier is built for the ML-DSA switch from the start.

The hybrid survives in two places only: classes where the boot-time numbers genuinely do not fit, and older SHE-class parts that cannot do ECC or fast SHA.

Concept · two boot models

Two boot models. One step makes the difference.

TC4xx secure boot · signature over CMAC03 / 20
Speaker notes

Both models start the same way: the OEM backend signs, and the bootloader verifies that signature at flashing.

The hybrid then adds a third step: after the update, the HSM computes a CMAC over the image with a device-unique key and stores it. Every later boot checks only that CMAC. The boot check therefore proves "unchanged since the MAC was computed", not "released by the OEM".

The recommended model simply removes that step. The HSM checks the same signature the bootloader checked. Same key, same manifest, one mechanism.

Concept · residual risk

The recompute gate is the hybrid's largest residual risk.

TC4xx secure boot · signature over CMAC04 / 20
Speaker notes

Whoever can trigger the CMAC recompute can make any image "valid" for every future boot. That gate can be reached through left-open debug access, a weak UDS 0x27 seed/key unlock, or an HSM that learns a MAC for whatever is in flash on its own.

Each of those paths must be controlled, tested and argued in the TARA and the R156 case. With signature at boot there is no gate: a tampered image fails against the public anchor, and there is no secret on the ECU that would help an attacker.

Read the table top to bottom: the hybrid wins one row, boot time, and by a few milliseconds on TC4xx. Signature at boot wins on what is actually proven, on what has to be protected on the ECU, and on how much has to be argued in the cybersecurity case.

The PQC row is a nuance: AES-CMAC is already quantum-resistant at the boot step, but the signature it depends on at flashing is not. The hybrid does not remove the PQC migration; it only hides it at flash time.

Method · per ECU class

Decision rule per ECU class.

TC4xx secure boot · signature over CMAC07 / 20
Speaker notes

Apply this per ECU class, not once for the whole fleet. Step one is the missing measurement: AES-CMAC over 2 MB on the actual target. Delta is signature time minus CMAC time.

Compare the delta with the headroom against that class's CAN wake-up or first-message deadline. If it fits, use signature at boot. If not, try staged verification before giving up. Only if staged verification also misses the deadline does the class stay on the hybrid, and then with the recompute gate controls on slide 16.

A dual-signed manifest carries both signatures. The boot policy decides whether one or both must pass.

TC4xx secure boot · signature over CMAC08 / 20
Speaker notes

The algorithm decision is a function of the same budget. Where 13 ms fits, go to ML-DSA now or run dual signatures. Where it does not, start with ECDSA but ship the verifier and the anchors that make ML-DSA a later policy change.

Crypto-agile here means concrete things: the manifest names its algorithm, the verifier dispatches on that ID, both anchors exist in OTP, and the boot policy can move in one direction only (ECDSA, then dual, then ML-DSA) so an attacker cannot downgrade it.

Option · staged verification

Try staged verification before falling back to the hybrid.

ManifestOne signature covers a manifest that lists a hash per segment.

Execution gateLater segments cannot run until their hash checks out.

Failure pathA background failure resets to the fallback image.

TC4xx secure boot · signature over CMAC09 / 20
Speaker notes

Staged verification keeps the signature model when the full verify is too slow for the first-message deadline. The HSM verifies the manifest signature and the boot-critical segment synchronously, that code starts and sends its first CAN frame, and the remaining segments are hashed in the background.

Three design points make it safe: the signed manifest lists per-segment hashes, so one signature still covers everything; nothing in a later segment may execute before its hash is checked; and a failed background check resets to the fallback image. The boot-critical part should not do anything that depends on the unverified rest.

Key management · flow

One signature, checked twice.

TC4xx secure boot · signature over CMAC10 / 20
Speaker notes

The backend signs a manifest containing the image hash, version, target ECU ID and the signature. The flash tool or OTA client only transports it.

The bootloader verifies the signature at flashing, before it erases or commits anything, and also checks the anti-rollback counter, the ECU ID or variant, and manifest dependencies. At every boot the HSM verifies the same signature with the same public anchor. One key, one signature, two checkpoints.

TC4xx secure boot · signature over CMAC11 / 20
Speaker notes

A natural question: if boot verifies anyway, why verify at flashing? Two reasons. First, a bad image is rejected before the working image is erased, so the ECU never bricks and the A/B or fallback slot stays usable. Second, flashing checks things boot does not need: the anti-rollback counter, the target ECU ID and variant, and dependencies between images.

The segment_hashes field is optional and only needed if a class uses staged verification.

Key management · where keys live

Private key in the backend. Public anchor on the ECU.

TC4xx secure boot · signature over CMAC12 / 20
Speaker notes

The private key lives only inside an HSM-based signing service in the OEM backend, with access control, dual control for production signing and audit logging of every request. It is never on the ECU, the flash tool or workshop equipment.

The ECU holds the public key in OTP or an HSM-protected key slot. Its secrecy does not matter; its integrity does. It must be immutable and write-protected after end of line.

Key management · hierarchy

A key hierarchy that survives a 15-year vehicle life.

TC4xx secure boot · signature over CMAC13 / 20
Speaker notes

The root key is offline and rarely used; only its hash sits in OTP, and it signs nothing but code-signing keys. Code-signing keys are scoped per ECU family or supplier, so a compromise affects one family and can be revoked without touching the root.

Development and production keys are strictly separate, and dev keys are disabled in OTP at end of line. UDS 0x29 authentication certificates, SecOC keys and TLS keys stay out of this tree: different purpose, lifecycle and owners.

Speaker notes

Because both anchors exist from day one, the move to ML-DSA is a signed policy update, not a hardware or OTP change on vehicles already in the field.

In the transition phase the backend signs every manifest twice. The policy can then require ECDSA only, both, or ML-DSA only, and can only move forward. Separately, plan for at least one code-signing key rotation during the vehicle life, using the reserved slots or the revocation counter.

Secure boot stops bad code from running. DICE lets the ECU prove what it booted. They fit together.

TC4xx secure boot · signature over CMAC19 / 20
Speaker notes

In the recommended model the code-signing private key is not per ECU. It belongs to an ECU family or supplier and stays in the backend HSM; every ECU of the family holds the same public anchor. The only per-ECU secret in the old design was the hybrid's CMAC key, which we remove.

Per-ECU private keys belong to device identity and attestation. With DICE, a device secret unique to each ECU is combined with measurements of each boot layer into compound device identifiers (CDIs). From them the ECU derives a stable DeviceID key, certified once at end of line, and an alias key that changes when the firmware changes. The backend checks that certificate chain to learn exactly what the ECU booted.

Appendix · DICE on TC4xx

Adding DICE to the TC4xx boot chain.

  1. HSM is the DICE root. Its boot stage reads the per-ECU device secret from OTP or a protected slot, derives the first CDI, then locks the secret until reset.
  2. Verify first, then measure. Reuse the hash from signature verification as the measurement. DICE adds almost no hashing time.
  3. Measure signer and version for derivation. The identity stays stable across signed updates. The exact image hash still goes into the alias certificate.
  4. Defer alias key generation. Attestation is not needed before the first CAN message, so the startup budget is untouched.
  5. Certify DeviceID at end of line with a separate device-identity CA, outside the code-signing tree.

What it enables

  • Attestation before OTA or diagnostic unlock
  • SecOC keys and TLS certs issued only to healthy ECUs
  • Clone detection through a certified identity
  • Hardware-bound UDS 0x29 authentication

Plan changes

  • OTP: device-secret slot with lock after read
  • Backend: device-identity CA with per-device revocation
  • End of line: DeviceID export and certificate issue
  • TARA: attestation as its own claim

To confirm with Infineon: PUF availability as the device secret source, and lock-after-read support in the HSM firmware. Call the DICE secret “device secret” in documents to avoid a clash with UDS diagnostics.

TC4xx secure boot · signature over CMAC20 / 20
Speaker notes

The HSM boot stage is the natural DICE root: it already owns the first measurement because it hashes the image to verify the signature. Reusing that hash keeps DICE cheap at boot, and moving the alias key generation after the first message keeps the startup budget from the decision rule intact.

Deriving the identity from signer and security version, not the raw hash, keeps keys and sealed data stable across legitimate updates. The device-identity CA is a new backend domain with its own revocation, alongside 0x29, SecOC and TLS.
